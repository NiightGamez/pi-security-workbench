# Lab Notes: Endpoint Detection Engineering — Linux Filesystem Canary Trap

## 1. Executive Summary & Concept
* **Objective:** Detect unauthorized file discovery, privilege escalation, and credential-harvesting activities on a Linux system before an attacker can weaponize them.
* **Core Idea:** Plant realistic "honeypot" (canary) files containing fake credentials in commonly targeted directories. Then, configure the Linux Audit Subsystem (`auditd`) to watch those files silently at the kernel level.
* **Why it Works:** Legitimate users and automated processes have zero reason to ever touch or inspect these fake files. Therefore, **any access is a high-fidelity indicator of compromise (IoC)** with a near-zero false-positive rate.

## 2. CompTIA CySA+ Exam Mapping
* **Primary Domain:** Security Operations and Monitoring / Incident Response.
* **Detection Mechanism:** **HIDS** (Host-Based Intrusion Detection System) / Endpoint Auditing.
* **ATT&CK Techniques Simulated:**
  * **T1083 (File and Directory Discovery):** Adversaries searching the file system for sensitive materials.
  * **T1552.001 (Credentials in Files: Local Files):** Searching config files, `.env` files, or bash history for passwords and API tokens.
* **Key Distinctions:**
  * `syslog` / `journald`: Records general application and service events (often manipulated or bypassed).
  * `auditd`: Hooks directly into the Linux kernel via system calls (`syscalls`). It cannot be bypassed by an attacker simply deleting their shell history (`.bash_history`).

## 3. Architecture & Mechanics: How `auditd` Works
The Linux kernel monitors all user-space requests through system calls. When a user runs `cat`, `nano`, or `stat`:
1. The binary issues a system call (e.g., `openat()`, `read()`, `statx()`) to the kernel.
2. The kernel's audit subsystem checks its active rule table (`auditctl -l`).
3. If the target path matches a monitored watch rule, the kernel generates an audit record and sends it to the `auditd` daemon.
4. `auditd` writes the structured log entry to `/var/log/audit/audit.log`.

### Breakdown of the Rule Syntax:
`-w /path/to/file -p rwa -k tripwire_aws`

* **`-w <path>` (Watch):** Specifies the absolute path to the directory or file to monitor.
* **`-p <permissions>`:** Defines which operations trigger the event:
  * `r` = Read (opening/viewing file contents).
  * `w` = Write (modifying or truncating the file).
  * `x` = Execute (running the file as a script/binary).
  * `a` = Attribute change (changing permissions, ownership, or timestamps with `chmod`, `chown`, `touch`).
* **`-k <key_name>` (Key Tag):** Attaches a custom, searchable metadata string to any events generated by this rule. This is critical for SOC triage, allowing you to instantly isolate alerts using `ausearch -k <key_name>` rather than parsing gigabytes of raw logs.

## 4. SOC Triage & Forensic Vocabulary
When analyzing the resulting telemetry, look for these key fields in the audit record:

| Field | Meaning | Forensic Significance |
|---|---|---|
| `type=SYSCALL` | The record type. | Indicates a raw kernel-level system call was captured. |
| `comm="..."` | Command name. | The short name of the process that accessed the file (e.g., `comm="cat"` or `comm="python3"`). |
| `exe="..."` | Executable path. | The full disk path to the binary (e.g., `/usr/bin/cat`). Useful for detecting masquerading or hijacked binaries. |
| `auid` | Audit User ID. | The **original** login UID. If an attacker logged in as `user1` (UID 1000) and elevated to `root` (UID 0), `auid` stays `1000`. This defeats privilege escalation spoofing. |
| `uid` / `euid` | User ID / Effective UID. | The active permissions under which the command ran at that exact millisecond. |
| `success=yes/no` | Operation Result. | Verifies whether the adversary succeeded in reading/writing the file or was blocked by file permissions. |
| `key="..."` | Rule Identifier. | The custom tag assigned in your audit rule (e.g., `key="tripwire_aws"`). |

## 5. Tooling Quick Reference
* **`augenrules --load`**: Compiles all `.rules` files located in `/etc/audit/rules.d/` into a single `/etc/audit/audit.rules` configuration and loads it directly into the running kernel.
* **`auditctl -l`**: Lists all currently active rules loaded into kernel memory.
* **`ausearch`**: Queries `/var/log/audit/audit.log` for specific parameters (e.g., `-k <key>` for tags, `-m <message_type>`, `-sv <result>`).
  * Using `--interpret` translates numeric UIDs, syscall numbers, and hex-encoded strings into human-readable text.
* **`aureport`**: Generates high-level aggregated summary reports (e.g., `-f` for file events, `--auth` for login attempts, `-i` for numerical translation).
